## 1. 風險清單

| # | 風險 | 等級 | 依據（研究證據） | 緩解 | 殘餘 |
|---|---|---|---|---|---|
| R1 | **上游漂移**：Superpowers 發布快（v6.3→v7.0 數週）、git-only、skills 內容常改；vendored 副本隨時間過時 | 🟡 | 研究 §2.3 | lockfile + sha256（verify-upstream）；PMMeeting release 才動 pin（可預測組合）；e2e 閉環測試守門；v2 `/pmmeeting upgrade` 給進階用戶 | vendored 版本永遠落後上游 latest — 這是 pinning 的固有代價，接受 |
| R2 | **OpenSpec 2.0 尚新**：2.0 是 1.x 的破壞性改版（skills-only、`delivery` 退役），CLI 介面（尤其 `instructions --json` 欄位）可能再變 | 🟡 | 研究 §3.1（2.0 changelog 大改） | pin 2.0.0 精確版；e2e 把 CLI JSON 輸出當契約測試；升級上游 = 顯式步驟（非自動跟 latest） | 上游 2.1 若破壞性改 JSON 契約 → 升級時需對齊（升級流程文件明列此檢查點） |
| R3 | **prompt 層脆弱（最核心）**：gate 只能驗證**可觀測狀態**（檔案、exit code、checkbox、commit 存在性），無法驗證模型**語意誠實**（例如「自稱」red 已跑、自稱 code review 有做） | 🔴→🟡 | Austin 摩擦點 3 的深層：紀律若只住 prompt 會失守 | 三層：① 狀態推進只能經 extension（無旁路）② gate 全部機械驗證 ③ TDD 證據要附 commit sha（extension 驗證 sha 存在於 git 歷史）；tests 本身在 green 時被真實執行（測試綠是客觀的）；task group 的 code review 用 reviewer 產出物（檔案/紀錄）而非口頭 | 模型仍能「偽裝」部分證據（如 red 階段跳過）— 殘餘依賴 TDD skill 紀律 + 人類抽查；v2 可加「red 輸出截圖/紀錄檔」式證據 |
| R4 | **skill 撞名 / 雙重 bootstrap**：用戶同時裝獨立 superpowers 套件時，其 extension 的 using-superpowers 注入與 PMMeeting 紀律並存，行為可能互相拉扯 | 🟡 | 研究 §1.2/§1.3；Superpowers extension 每請求注入 | vendored skills 不暴露（零撞名）；doctor 偵測獨立安裝並**建議卸載 superpowers 套件**（PMMeeting 是超集）；不阻止共存 | 用戶不聽建議堅持共存 → 雙 bootstrap 並存，紀律衝突由用戶自負（文件明載） |
| R5 | **context/token 膨脹**：15 vendored skills + orchestrator + bootstrap 注入 | 🟡 | Pi skills 以 name+description 列表進 context（輕）；內容才重 | 只注入**路徑表**（~60 行上限），skill 內容 per-phase 才 read；未初始化 project 零注入 | 每 phase 多一次 read 的延遲 — 可接受 |
| R6 | **subagent 可用性不確定**：P5 已定案 **subagent 優先**，依賴 `pi-subagents` 等提供 `subagent` 工具；偵測方式需確認 | 🟡 | Superpowers 文件明言 Pi 無標準 subagent 工具 | 偵測到 `subagent` 工具 → subagent-driven-development（預設）；偵測不到/失敗 → 自動 fallback executing-plans 並告知用戶（偵測在 P4 實作期以 Pi API 確認；fallback 不阻塞） | 無 subagent 用戶失去雙代理 review 的品質加成（fallback 仍可完整跑完） |
