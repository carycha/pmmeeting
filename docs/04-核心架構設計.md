# PMMeeting 核心架構設計

> 每個關鍵決策附 ≥2 替代方案與取捨；結尾是目錄結構、extension 設計與安裝矩陣。

---

## 1. 關鍵決策

### D1 上游代碼管理（核心決策）

**問題**：如何在「不修改上游一字节」+「用戶免預裝」+「可 pin 版本可升級」三者之間取得平衡？

#### D1a — OpenSpec CLI（v2.0.0，npm 套件）

| 方案 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| **A. npm dependency（採納）** | `package.json: dependencies { "@fission-ai/openspec": "2.0.0" }`（精確 pin） | Pi 安裝 git/npm 套件時**自動** `npm install` 依賴（已查核原始碼）→ 免預裝；unpacked 僅 ~2.5MB；版本 pin 由 package.json + npm lock 承擔；升級 = 改 version 重發布 | 需要 Node ≥22.12（Pi 本身要求 ≥22.19，天然滿足） |
| B. standalone binary vendored | 把編譯好的 `openspec` 二進位（每平台）放進 repo | 免 Node、啟動快 | 要管多平台二進位（linux/mac/win × arch）、更新麻煩、repo 膨脹、繞過 npm 生態 |
| C. 要求用戶預裝 CLI | 文件寫「請先 `npm i -g openspec`」 | 套件最小 | 直接違反需求 4（免預裝）；PATH 不確定、版本不受控 |

**採納 A**。extension 解析 CLI 路徑：`<packageRoot>/node_modules/.bin/openspec`（絕對路徑，不依賴 PATH、不依賴用戶安裝）。

#### D1b — Superpowers skills（v7.0.2，git-only 分發）

| 方案 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| A. git submodule | `upstream/superpowers` 為 submodule 指向 pin tag | 上游 diff 一目了然、升級 `git submodule update --remote` | 用戶 `pi install` 後 Pi 只做 `git clone`（**不初始化 submodule** — 已查核 `installGit()` 只 clone+checkout+npm install）→ 裝完是空目錄，除非我們改 Pi 或要求用戶手動 `git submodule update --init`。★致命傷 |
| B. git subtree | `git subtree pull` 進 `upstream/superpowers/` | clone 即完整；無 .gitmodules | 歷史噪音（subtree merge commits）；升級流程較重；對下游用戶等同 C（已攤平） |
| **C. vendored copy + lockfile + sync 腳本（採納）** | 維護者跑 `scripts/sync-superpowers.mjs v7.0.2`：clone pin tag → 複製 `skills/`（+ 必要附檔）到 `upstream/superpowers/` → 生成 `upstream/superpowers.lock.json`（repo/tag/commit/逐檔 sha256）→ commit | 對 Pi 完全透明（clone 即可用，零特殊操作）；byte-identical 可由 checksum 證明；lockfile 同時是「版本 pin 聲明」；升級 = 維護者跑腳本 + 發布新版（上游 diff 用 git 在腳本內生成並附在 PR）；**社群先例**：strelov1 的 `vendor-superpowers.mjs` | repo 內有上游副本（~百KB 級，可接受）；上游改動要等 PMMeeting 發布（見 D1c） |
| D. 要求用戶另裝 superpowers Pi 套件 | PMMeeting 宣告「peer」慣例：`pi install git:github.com/obra/superpowers` | 零 vendoring | 違反需求 4（免預裝）；兩套件各自漂移、bootstrap 雙重注入、skill 撞名 → 全盤皆輸 |

**採納 C**。誠實声明：vendoring 是「複製品 + 校驗」，不是「同步視圖」；上游升級透過 D1c 的兩層機制。

#### D1c — 升級機制（兩層）

| 層 | 機制 | 說明 |
|---|---|---|
| 主層（v1） | **PMMeeting release pin 雙上游**：發布 = lockfile（Superpowers tag/commit/sha256）+ package.json（OpenSpec 精確版本）。用戶升級上游 = 升級 PMMeeting（`pi update`） | 可預測、可測試（每個 PMMeeting 版本對應一組驗證過的上游組合） |
| 進階層（v2） | `/pmmeeting upgrade`：查詢 npm（openspec）與 git ls-remote（superpowers tags）新版本 → 顯示 changelog → 在**本機安裝目錄內**執行 sync 腳本 + npm install 新 pin → 更新 lockfile 副本 | 給想要 bleeding-edge 的用戶；失敗回滾；不影響已發布版本的語義 |
| 守衛 | `/pmmeeting doctor` 永遠顯示「上游版本 × PMMeeting pin」對照，漂移即黃灯 | 任何手改都能被發現 |

### D2 vendored Superpowers skills 的暴露方式

| 方案 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| A. 暴露進 `pi.skills` | vendored 15 skills 成為 Pi 可自動觸發 skill | 用戶離 PMMeeting workflow 也能用 | 與用戶生態中任何同名單身 superpowers 安裝**撞名**（first-wins + collision 警告，行為隨 settings 順序而變）；skill description 自動觸發會與 PMMeeting phase 紀律打架（例如 build 中模型自動觸發 brainstorming） |
| **B. 不暴露、orchestrator 絕對路徑 read（採納）** | `pi.skills` 只列 PMMeeting 自己的 skill；vendored skills 是「參考庫」，orchestrator 在 phase 入口指令中給出絕對路徑（extension 注入的 skill 路徑表） | 與任何同名單身安裝**零衝突**（連 warning 都沒有）；觸發時機完全由狀態機控制（正合 Austin 摩擦點 3 的修法）；vendored 內容保持 byte-identical 且不會被 Pi skill loader 的驗證規則意外卡住 | 用戶在 PMMeeting 之外不能直接 `/skill:brainstorming`（想單獨用請裝官方 superpowers 套件 — doctor 會指引） |
| C. 改名暴露（`pmmeeting-brainstorming`…） | 複製並改 frontmatter name | 不撞名 | 改 frontmatter = 改上游碼（違反需求 1）；名稱不自然、自動觸發語意錯亂 |

**採納 B**。副作用管理：extension 的 doctor 掃描 settings 中的 superpowers/openspec 套件與 `.agents/skills`，若偵測到獨立安裝 → 提示（不阻止；兩者可共存，只是各自獨立運作）。

### D3 編排模型

| 方案 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| A. 純模型驅動 | 一切編排寫在 orchestrator skill 的 prompt 裡；extension 只註冊 `/pmmeeting` 命令 | 實作最快；模型靈活 | gate 可被模型「忘記」或「自以為通過」— 正是 Austin 摩擦點 3；狀態只能靠模型自述，恢復脆弱 |
| B. 純代碼驅動 | extension 把整個狀態機、每 phase 的完整指令都寫死在 TS 裡，skill 只是被 read 的資料 | 機制最硬 | 把 workflow 語意鎖進代碼：上游 skill 一改版就要改代碼；extension 體積大、迭代慢；失去 skill 生態的可讀性/可移植性 |
| **C. 混合：extension = 機制，skill = 判斷（採納）** | extension 只負責**不可談判的部分**：state 檔案、gate 驗證（檔案檢查 + CLI 執行）、TDD 證據、CLI 路徑解析、skill 路徑表注入；orchestrator skill 負責**可判斷的部分**：phase 內如何與用戶對話、何時讀哪個 skill、如何處理例外。phase 推進只能透過 extension 工具（模型沒有寫 state 的其它路徑） | gate 不可繞過（機制保證）；workflow 語意留在 skill（文字、易迭代、與上游 skill 同語言）；上游升級通常只動 skill 文本不動 extension 代碼 | 需要清楚劃分「哪些檢查進 gate、哪些留在指令」— v1 範圍見 03 文件 G1-G6 |

### D4 狀態檔案位置

| 方案 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| A. 專案級單一 `.pmmeeting/state.json` | 只允許一個 active change | 最簡 | OpenSpec 原生支援多 active changes；強制串行違反上游模型；換 change 要搬遷 state |
| **B. 每 change 共置 `openspec/changes/<id>/.pmmeeting.json`（採納）** | change 樹自含（含 PMMeeting state）；project.json 只放指針與全局資訊 | 與 OpenSpec「change = 工作單位」對齊；change 歸檔 = state 自然進入 archive 歷史；git 上可審（每 change 的 phase 歷史）；多 change 並存天然支援 | 檔案多一分（可忽略）；需處理「非 PMMeeting change 沒有 state」的邊界（03 §3） |
| C. 無 state、純從工件推導 | phase 由「哪些檔案存在」推斷 | 零同步問題 | 推導模糊（design.md 存在但被否決？tasks.md 半勾選是 build 還是 verify 失敗回退？）；gate 歷史/TDD 證據無處放 |

**採納 B**（+ project.json 指針）。

### D5 OpenSpec schema 策略

| 方案 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| **A. 內建 `spec-driven` schema + orchestrator 契約（v1 採納）** | 直接用 OpenSpec 內建 schema；tasks.md 的 TDD 結構（每 task 含 test 先）由 writing-plans 的契約在 P4 保證 | 零自訂 schema 維護負擔；上游 schema 升級自動跟上；v1 最快到可用 | TDD task 結構靠 prompt 契約而非 schema 模板強制（v2 可補） |
| B. 自訂 `pmmeeting` schema（v2 評估） | `schemas/pmmeeting/`（YAML + templates，放於 PMMeeting 套件、init 時裝進 project 的 `openspec/schemas/`）把 TDD task 模板、deviation 區段等烤進模板 | workflow 成為「工具可檢查的契約」（superspec/Austin 的共識）；模板強制 TDD 結構 | 多一套模板要跟上游 spec-driven 同步；OpenSpec 2.0 尚新，schema 介面可能再變 |

**v1 採 A、v2 依實戰痛點決定 B**（若 P4/P5 的 task 結構失守率顯著）。

### D6 命令面

| 方案 | 做法 | 採納 |
|---|---|---|
| A. 單一 `/pmmeeting` + 子參數 | `/pmmeeting [init\|new\|status\|doctor\|upgrade\|abandon]` | **是** — 單一入口（需求 2）、命名空間乾淨、補全好做 |
| B. 多頂層命令 | `/pm-explore`、`/pm-propose`… | 否 — 命令污染、與 openspec-* 命名混淆 |

### D7 語言（已定案 2026-07：哥拍板）

- PMMeeting **自己**的 skill 本文與注入文本：**繁體中文為主**（description 含中英文關鍵詞以利觸發）；上游 skills 維持英文原樣（不改）。
- 文件：繁體中文。
- 工件（design.md/tasks.md…）：跟隨 project 語言（orchestrator 指令：「用 project 的主要語言寫」，預設繁體中文）。

## 2. 目錄結構（pmmeeting/）

```
pmmeeting/
├── package.json                 # pi 套件 manifest；pi: { extensions, skills }
│                                #   dependencies: { "@fission-ai/openspec": "2.0.0" }
├── README.md                    # 使用者入口
├── LICENSE
├── extensions/
│   └── pmmeeting.ts             # 唯一 extension：commands + tool + events（機制層，~500 行目標）
├── skills/
│   └── pmmeeting/
│       └── SKILL.md             # orchestrator（PMMeeting 唯一自己的 skill）
│                                #   phase 入口指令、工件重導向契約、skill 路徑表引用
├── upstream/
│   ├── superpowers/
│   │   ├── skills/…             # v7.0.2 的 15 skills，byte-identical（sync 腳本產出）
│   ├── superpowers.lock.json    # { repo, tag, commit, fetchedAt, files: {path: sha256} }
│   └── README.md                # 來源、pin、sync 用法（維護者文件）
├── scripts/
│   ├── sync-superpowers.mjs     # 維護者：clone pin tag → 複製 + 生成 lockfile + diff 報告
│   └── verify-upstream.mjs      # CI/doctor：checksum 驗證 byte-identical
├── docs/                        # 本設計文件 + 使用者指南（實作後擴充）
├── tests/
│   ├── unit/                    # extension 邏輯（gate、state、CLI 解析）
│   └── e2e/                     # 玩具 project 上跑完整 7 phase 的煙霧測試腳本
└── .gitignore
```

**安裝進用戶機器後的實際位置**（git 來源）：`~/.pi/agent/git/github.com/carycha/pmmeeting/`（Pi 管理，`pi update` 刷新）；CLI 在 `…/node_modules/.bin/openspec`。

## 3. Extension 設計（`extensions/pmmeeting.ts`）

### 3.1 模組劃分

| 模組 | 職責 |
|---|---|
| `resolve.ts` | packageRoot（extension 自身路徑推得）、CLI 路徑（node_modules/.bin/openspec，含缺失時修復提示）、skills 絕對路徑表（15 vendored + 1 pmmeeting）、project 偵測（向上找 `.pmmeeting/project.json` 或 `openspec/`） |
| `state.ts` | project.json / .pmmeeting.json 的 schema 定義、讀寫（原子寫）、驗證、phase 常數與遷移表 |
| `gates.ts` | G1-G6 驗證器（檔案存在性、tasks.md checkbox 解析、spawn `openspec validate --json`、test 命令執行） |
| `cli.ts` | openspec CLI 的薄封裝（spawn、timeout、JSON parse、錯誤包裝） |
| `commands.ts` | `/pmmeeting` 六個子命令 |
| `tool.ts` | `pmmeeting` 工具（status/new/advance/gate/record-tdd/abandon/doctor） |
| `bootstrap.ts` | `session_start` 狀態行 + `context` 注入文本（未初始化 project 靜默） |

### 3.2 行為要點

- **所有 state 寫入只在 tool handler 內**（gate 通過才寫）；`advance` 回傳「下 phase 指令包」= 該 phase 的 orchestrator skill 區段路徑 + openspec skill 名 + 工件契約摘要 → 模型照做。
- **CLI 一律經 `cli.ts`**：統一 cwd=project root、env（`OPENSPEC_NO_UPDATE_CHECK=1` 避免背景檢查干擾）、超時、JSON 解析。
- **注入節制**：context 注入上限 ~60 行（狀態 + 路徑表 + 一句紀律），避免 token 膨脹；未初始化 project 零注入。
- **錯誤語言**：面向用戶輸出繁體中文（與 D7 一致），錯誤附可執行修復建議。
- **不依賴 Pi 特定事件順序**：所有恢復邏輯以檔案為準。

### 3.3 測試策略

- unit：gates（各種 tasks.md 狀態、壞 state 檔、CLI mock）、state（schema 驗證、原子寫）、resolve（路徑解析）。
- e2e：fixture 玩具 repo（小 Node 專案 + 測試命令）→ 以 Pi SDK/CLI headless 跑 `/pmmeeting init → new → …`，斷言每 phase 後檔案樹與 state 符合預期；**包含「compaction 模擬」**（新 session 重進）驗證恢復。

## 4. 安裝矩陣（需求 5、6）

| 情境 | 指令 | 說明 |
|---|---|---|
| 本地開發 | `pi install /path/to/pmmeeting`（local source）或 `pi -e /path/to/pmmeeting/extensions/pmmeeting.ts`（免安裝迭代） | 改 extension 即重載；`scripts/sync-superpowers.mjs` 本地跑上游同步 |
| 正式安裝（git） | `pi install git:github.com/carycha/pmmeeting`（可帶 ref pin） | Pi clone + 自動 npm install（OpenSpec CLI 進 node_modules） |
| 正式安裝（npm，發布後） | `npm publish`（`pi-package` keyword）→ `pi install npm:@carycha/pmmeeting`（已定案） | 進 pi.dev/packages gallery |
| 專案級安裝 | 任一指令加 `--local` | 寫入 `.pi/settings.json`，只對該 project 生效 |
| 升級 | `pi update`（刷新套件本身）；v2：`/pmmeeting upgrade`（套件內上游 pin） | doctor 隨時顯示版本對照 |
