# PMMeeting 整合對照表

> 核心原則：**OpenSpec 擁有所有持久文件**（`openspec/` 樹是唯一文件真相來源）；**Superpowers 提供流程紀律**（skills，vendored、不改一字）；**PMMeeting 是編排層**（phase 映射、工件重導向、狀態機與 gate）。
> 任何 Superpowers 上游 skill 預設會寫出的獨立文件（`docs/superpowers/...`），在 PMMeeting workflow 內一律重導向到 OpenSpec 工件 — 由 PMMeeting 自己的 orchestrator skill 以「明確指令」覆蓋上游預設路徑（orchestrator/用戶指令優先於 skill 內建預設，與 Superpowers 自家 bootstrap 的機制相同），**上游 skill 檔案保持 byte-identical**。

## 1. Phase ↔ 雙上游對照（v1 主流程）

| # | Phase（狀態） | OpenSpec 側（誰做） | Superpowers 側（誰做） | PMMeeting 橋接（自己的層） | 唯一產出工件 | Gate（通過才推進） |
|---|---|---|---|---|---|---|
| P0 | `setup`（每 project 一次） | 官方 `openspec init --tools pi`（bundled CLI 執行） | —（`using-git-worktrees` 在 P3 才用） | `pmmeeting` extension 的 init 流程：跑官方 init、校驗 CLI 版本、寫 project state、偵測與獨立安裝的 superpowers/openspec 衝突 | `openspec/` 樹（官方產出）+ `.pmmeeting/project.json`（版本與設定） | `openspec validate --changes` 通過、state 已寫、doctor 全綠 |
| P1 | `explore` | `openspec-explore` skill（讀 codebase、思考夥伴） | 不強制（避免 Austin 摩擦點 2 的反向：brainstorm 不讀碼 → 所以 explore 先） | orchestrator 指令：UI 工作必須把 mock 存成 `openspec/changes/<id>/mocks/*.html`（檔案化，摩擦點 1）；結束時建立 change：`openspec new change <id>` | 對話共識；`openspec/changes/<id>/` 骨架 | 用戶確認「要做」+ change 已建立 |
| P2 | `design` | change 的 `design.md`（OpenSpec 原生工件） | `brainstorming` skill（設計探索、Approaches 比較、自我審查） | **重導向契約**：brainstorming 的 design doc 直接寫入 `openspec/changes/<id>/design.md`（非 `docs/superpowers/specs/`）；mocks 以路徑引用進 design.md | `openspec/changes/<id>/design.md`（+ `mocks/`） | 人類批准 design（brainstorming 的硬性要求，保留）+ 存在性檢查 |
| P3 | `propose` | `openspec-propose` skill（產出 proposal + specs deltas，套用 schema 管線） | —（brainstorming 已於 P2 完成） | orchestrator 指令：proposal 必須引用已批准的 design.md 路徑；specs deltas 覆蓋 design 中所有 Requirement | `proposal.md`、`specs/<cap>/spec.md`（deltas） | `openspec validate --change <id> --json` 通過（機器 gate） |
| P4 | `plan` | change 的 `tasks.md`（OpenSpec 原生工件，`- [ ]` checkbox 結構） | `writing-plans` skill（bite-sized task 拆解、TDD 結構、DRY/YAGNI） | **重導向契約**：writing-plans 的 plan 直接寫入 `openspec/changes/<id>/tasks.md`（非 `docs/superpowers/plans/`）；每個 task 綁定「test 先」結構與驗收條件；**不另外產生第二份 plan 檔** | `openspec/changes/<id>/tasks.md`（唯一 plan） | 用戶批准 tasks + 結構檢查（每 task 可獨立驗證） |
| P5 | `build` | `openspec-apply-change` skill（依 `openspec instructions apply --change <id> --json` 逐 task 執行、回寫 checkbox） | `test-driven-development`（每 task：red→green→refactor→commit）＋ **subagent 優先**（已定案）：偵測到 subagent 工具 → `subagent-driven-development`（implementer + reviewer 雙子代理）；無 → fallback `executing-plans`（本機逐 task） | 狀態機機制化（解決 Austin 摩擦點 3）：extension 的 `pmmeeting` 工具記錄 phase 與每 task 的 TDD 證據；每 task group 結束後強制 `requesting-code-review`（有 subagent）或 `verification-before-completion`（無）；TDD 紀律由 P5 入口指令 + state 檢查雙重保證，**不靠模型記憶** | 程式碼 + 測試（git 歷史）、`tasks.md` 勾選進度（OpenSpec 原生帳本） | 每個 task：test 存在且紅過（TDD 證據）→ 綠 → 勾選；全數勾選後進入 verify |
| P6 | `verify` | `openspec-verify-change` skill（實作 vs specs/tasks/design 三方比對） | `verification-before-completion`（完成前驗證：跑全部測試、證據先於宣稱） | 比對結果與偏差記錄寫回 `openspec/changes/<id>/verify.md`（PMMeeting 新增工件，唯一天然新增文件） | `verify.md`（deviations 清單） | verify 無未解決 deviation（或用戶明示接受） |
| P7 | `archive` | `openspec-archive-change` skill（归档到 `changes/archive/`、specs 併入 `openspec/specs/` source of truth） | `finishing-a-development-branch`（分支收尾決策：merge/PR/cleanup）＋ **retro 契約**（解決摩擦點 5） | retro 寫入 `openspec/changes/archive/<id>/retro.md`（新學到新 constraint 的項目同步 append 到 project memory 檔） | 歸檔後的 change + `openspec/specs/` 更新 + `retro.md` + project memory 更新 | `openspec archive` 成功 + retro 存在 |

### 迴路（非線性）

- `build` 發現 spec 錯 → 回 `propose`（OpenSpec 原生 loop，保留）。
- `verify` 發現實作偏離 → 回 `build`（補 task）。
- `retro` 發現「本該是 requirement 的 constraint」→ 開新 change 回 `explore`。

## 2. 重複工件消解對照（單一真相來源的核心）

| 概念 | Superpowers 上游預設 | OpenSpec 原生 | **PMMeeting 裁定（v1）** |
|---|---|---|---|
| 設計文件 | `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` | `openspec/changes/<id>/design.md` | → 寫 `design.md`，**不寫** docs/superpowers/ |
| 實作計畫 | `docs/superpowers/plans/YYYY-MM-DD-<feature>.md` | `openspec/changes/<id>/tasks.md` | → 寫 `tasks.md`，**不寫** docs/superpowers/；plan 與 tasks 是同一份東西 |
| 執行進度 | plan 檔內手工標記 / ledger | `tasks.md` 的 `- [ ]` checkbox（`apply-change` 原生回寫） | → 只用 `tasks.md` checkbox；PMMeeting state 檔**不重複存** task 進度（只存 phase 與 TDD 證據索引） |
| UI mock | 無（對話中揮發） | 無 | → `openspec/changes/<id>/mocks/`（PMMeeting 新增目錄） |
| 驗收偏差 | 無 | 無 | → `openspec/changes/<id>/verify.md`（PMMeeting 新增） |
| 教訓/retro | 無（對話蒸發） | archive 無 retro 概念 | → `openspec/changes/archive/<id>/retro.md` + project memory（PMMeeting 新增） |
| 專案常規/pitfalls | 無 | 無 | → project memory 檔（建議 `AGENTS.md` 的 PMMeeting 區塊，避免再造一個平行文件） |
| 能力行為真相 | 無 | `openspec/specs/<cap>/spec.md`（archive 後合併） | → 唯一長期行為文件（OpenSpec 原生，不動） |

**結果**：一個 change 的全生命周期文件 = `openspec/changes/<id>/` 一棵樹（proposal、specs deltas、design、tasks、mocks、verify、state、retro@archive）＋ git 歷史。`docs/superpowers/` 在 PMMeeting 管理的 project 中**不出现**。

## 3. Skill 調用對照（誰、何時、怎麼調）

| Skill（來源） | 調用時機 | 調用方式（機制） |
|---|---|---|
| `openspec-*` 12 個（OpenSpec 官方，project 端 `.agents/skills/`） | P1/P3/P5/P6/P7 各階段 | 模型以 skill 名觸發（Pi 自動發現）；orchestrator 在每個 phase 入口**指名**要用的 openspec skill（機制化，摩擦點 3） |
| `brainstorming`、`writing-plans`、`test-driven-development`、`subagent-driven-development` / `executing-plans`、`requesting-code-review`、`verification-before-completion`、`using-git-worktrees`、`finishing-a-development-branch`（Superpowers vendored） | P2/P4/P5/P6/P7 | **絕對路徑 read**（orchestrator 指令：`read <packageRoot>/upstream/superpowers/skills/<name>/SKILL.md`）→ 不受 skill 名稱衝突影響（04-D2） |
| `systematic-debugging`（Superpowers vendored） | 任何 phase 遇 bug | 同上行絕對路徑；不受 phase 限制 |
| `pmmeeting`（PMMeeting orchestrator skill，**PMMeeting 唯一自己的 skill**） | `/pmmeeting` 或用戶自然語言觸發 | 由 extension 的 `/pmmeeting` 命令載入；持狀態機契約、phase 入口指令、工件重導向契約 |

> 設計要點：vendored Superpowers skills **不**進入 `pi.skills`（不暴露成 Pi 可自動觸發的 skill），只作為 orchestrator 的「參考文件庫」被絕對路徑讀取 → 與用戶生態中任何同名單身安裝零衝突。

## 4. CLI 調用對照（PMMeeting extension 的 mechanism 層）

| 用途 | 命令（已於 v2.0.0 原始碼核對） |
|---|---|
| 建立 change | `openspec new change <id>` |
| 產出 artifact 指令 | `openspec instructions <proposal\|specs\|design\|tasks> --change <id> --json` |
| 執行期指令（含 task 的 sourcePath/line） | `openspec instructions apply --change <id> --json` |
| 驗證 | `openspec validate --change <id> --json`（或 `--changes`） |
| 狀態 | `openspec status [--json]` |
| 歸檔 | `openspec archive <id>` |
| 專案初始化 | `openspec init --tools pi`（寫入 `.agents/skills/openspec-*` + `.pi/skills/` symlinks） |
| 版本對齊 | `openspec update`、`openspec version` |
| CLI 路徑解析 | `<pmmeeting-package-root>/node_modules/.bin/openspec`（extension 從自身所在套件目錄解析，絕不依賴 PATH） |
