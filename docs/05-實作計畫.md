# PMMeeting 分階段實作計畫

> 原則：每個 phase 結束都有**可安裝、可驗證**的增量（verification-before-completion 精神）；先機制後智能（先讓 gate/state/CLI 硬起來，再打磨 workflow 語意）；每 phase 列驗收標準（AC），未達 AC 不進下一 phase。

---

## Phase 0 — 倉庫骨架 + 上游 vendoring 工具鏈（機制地基）

**目標**：repo 可被 `pi install <local>` 且 vendoring 流程可重複執行。

| # | 任務 |
|---|---|
| 0.1 | 初始化 repo（git init 已有 remote；加 README 骨架、LICENSE、`.gitignore`） |
| 0.2 | `package.json`：pi manifest（`pi-package` keyword、`pi.extensions/skills`）、`dependencies: { "@fission-ai/openspec": "2.0.0" }`、scripts |
| 0.3 | `scripts/sync-superpowers.mjs <tag>`：clone pin tag → 複製 `skills/` 至 `upstream/superpowers/skills/` → 生成 `superpowers.lock.json`（tag/commit/逐檔 sha256）→ 輸出與現狀的 diff 摘要 |
| 0.4 | `scripts/verify-upstream.mjs`：按 lockfile 校驗 byte-identical（CI 用、doctor 用） |
| 0.5 | 執行 0.3 pin **v7.0.2**，commit vendored skills + lockfile |
| 0.6 | CI（GitHub Actions）：`verify-upstream` + `npm test`（先空跑） |

**AC**：
- [ ] `pi install /media/.../pmmeeting` 成功，`pi list` 顯示套件
- [ ] `npm run verify-upstream` 綠；手改任一 vendored 檔後 verify 紅（可偵測）
- [ ] lockfile 含 v7.0.2 commit 與全檔 sha256

## Phase 1 — 最小 Pi 套件（可安裝、可診斷）

**目標**：`/pmmeeting doctor` 與 `/pmmeeting status` 可用；CLI 解析正確。

| # | 任務 |
|---|---|
| 1.1 | `extensions/pmmeeting.ts` 骨架：`resolve.ts`（packageRoot、CLI 路徑、project 偵測、skill 路徑表） |
| 1.2 | `cli.ts`：openspec spawn 封裝（cwd、env、timeout、JSON、錯誤） |
| 1.3 | `commands.ts`：`/pmmeeting`（含 `doctor`、`status` 子命令）＋ argument completion |
| 1.4 | `doctor` 實作：CLI 可執行性、版本對照（lockfile × node_modules × openspec version）、獨立 superpowers/openspec 安裝偵測（掃描 pi settings + `.agents/skills`）、project 初始化狀態、壞 state 偵測 |
| 1.5 | `skills/pmmeeting/SKILL.md` v0（orchestrator 骨架：狀態報告 + 「尚未實作」路標） |
| 1.6 | unit tests：resolve、cli（mock）、doctor |

**AC**：
- [ ] 未初始化 project：`/pmmeeting` 顯示狀態 + 引導 `init`；`/pmmeeting doctor` 全綠（除「未初始化」黃灯）
- [ ] 與獨立安裝的 superpowers 共存：doctor 偵測並提示，無 crash、無 skill 撞名 warning（vendored 未暴露）
- [ ] 所有 unit tests 綠

## Phase 2 — 狀態機 + P0/P1（setup、explore、new）

**目標**：`init` 能正確初始化 project；`new` 建立 change 並進入 explore。

| # | 任務 |
|---|---|
| 2.1 | `state.ts`：schema、原子寫、驗證、遷移表；project.json + .pmmeeting.json |
| 2.2 | `gates.ts`：G1 |
| 2.3 | `tool.ts`：`pmmeeting` 工具（status/new/advance/gate/record-tdd/abandon/doctor 骨架；先實作 status/new/advance） |
| 2.4 | `/pmmeeting init`：偵測已初始化（idempotent）→ 跑 `openspec init --tools pi`（經 cli.ts）→ 校驗產出（`.agents/skills/openspec-*` 存在）→ 寫 project.json |
| 2.5 | `/pmmeeting new <id>`：`openspec new change <id>` + 初始化 change state（phase=explore）+ 設 activeChange |
| 2.6 | `bootstrap.ts`：session_start 狀態行 + context 注入（含 skill 路徑表；未初始化靜默） |
| 2.7 | orchestrator skill v1：P1 explore 段（openspec-explore 指名、mock 檔案化契約、G1 確認指令） |
| 2.8 | e2e fixture 玩具 repo + e2e 腳本（init→new→explore 完成→G1） |

**AC**：
- [ ] 玩具 project `init` 兩次不報錯（idempotent）；`.agents/skills/openspec-*` 與 `.pi/skills/` symlink 正確
- [ ] `new` 後 `openspec/changes/<id>/.pmmeeting.json` phase=explore；`advance` 在 G1 條件未滿時被拒
- [ ] 新 session 重進：session_start 顯示正確狀態行（恢復驗證）

## Phase 3 — 規格側（P2 design、P3 propose、P4 plan）

**目標**：從 explore 到 tasks.md 批准的全鏈路，工件全部落在 change 樹。

| # | 任務 |
|---|---|
| 3.1 | `gates.ts`：G2、G3（`openspec validate --json` 整合）、G4 |
| 3.2 | orchestrator skill v2：P2 design 段（brainstorming 絕對路徑 read + **design.md 重導向契約**）、P3 propose 段（openspec-propose 指名 + 引用 design.md 路徑契約）、P4 plan 段（writing-plans read + **tasks.md 重導向契約** + TDD task 結構契約） |
| 3.3 | advance 回傳「指令包」機制落地（phase→{skill 路徑, openspec skill 名, 契約摘要}） |
| 3.4 | e2e：explore→design→propose→plan 全跑，斷言**不產生** `docs/superpowers/` 任何檔案、validate 通過 |

**AC**：
- [ ] 完整跑一個小 change 到 plan 批准：change 樹內 proposal/design/specs deltas/tasks 齊全
- [ ] `docs/superpowers/` 不存在（重導向生效）
- [ ] 每 gate 的「不通過」路徑都有 e2e 覆蓋（壞 tasks、validate 失敗）

## Phase 4 — 執行側（P5 build、TDD 機制化）

**目標**：build 迴圈 + TDD 證據 + 執行模式二擇一（subagent / inline）。

| # | 任務 |
|---|---|
| 4.1 | `record-tdd` 實作 + G5（checkbox 計數 + TDD 證據齊全 + git 乾淨） |
| 4.2 | orchestrator skill v3：P5 build 段（apply-change 指名、`instructions apply --json` 消費、TDD 紀律指令、**subagent 優先**選擇邏輯：偵測到 subagent 工具 → subagent-driven-development；無 → fallback executing-plans（已定案）、task group 收尾的 code-review 指令） |
| 4.3 | 有 subagent 路徑（pi-subagents 安裝下）e2e 主驗 + 紀錄 |
| 4.4 | 無 subagent 工具的 fallback 路徑（本機 executing-plans）e2e |
| 4.5 | 迴路指令：spec 錯回 propose（state 保留、tasks.md 處理策略） |

**AC**：
- [ ] 玩具 change 在 e2e 中完成 build：每 task 有 red/green 證據、tasks.md 全勾、commit 歷史符合 TDD 節奏
- [ ] 拔除 TDD 證據路徑後 G5 拒絕推進（機制保證，非 prompt 保證）
- [ ] subagent 與 inline 兩路徑皆可跑通（subagent 至少手動驗證一次）

## 估算與順序依賴

```
P0（地基）─▶ P1（可安裝）─▶ P2（setup/explore）─▶ P3（規格側）─▶ P4（執行側）─▶ P5（收口+硬化）─▶ P6（發布）
```

- 關鍵路徑：P3（重導向契約的 prompt 調試）與 P4（TDD 機制化）最易超估 — 各留緩衝。
- P2-P5 每個 phase 產出都可獨立使用（init/status 先可用、規格側先可用）。
- 全程不改動 `upstream/superpowers/` 任何檔案（sync 腳本唯一寫入者）。

## 完成定義（v1.0）

1. 需求 1-7 全數滿足（01-06 文件對照）。
2. 乾淨環境 e2e 閉環綠。
3. 兩個真實專案（哥指定或自選）各跑完一個完整 change，retro 記錄在檔。
