## 1. Pi Coding Agent（宿主平台）

**版本**：v1.5.2（`@earendil-works/pi-coding-agent`，Node ≥ 22.19）

### 1.1 套件（Package）機制

- 套件 = 一般目錄或 npm package；`package.json` 的 `pi` key 宣告資源：
  ```json
  { "pi": { "extensions": ["./extensions/x.ts"], "skills": ["./skills"], "prompts": ["./prompts"], "themes": ["./themes"] } }
  ```
- 含 `pi-package` keyword 的 npm package 會上架 pi.dev/packages gallery（已查核 gallery 上多個含依賴的套件：pi-subagents、pi-extensions(8.9MB)、pi-agent-browser-native 等 → **打包大型依賴是常態**）。
- 安裝來源：`pi install npm:<pkg>` / `pi install git:<repo>` / `pi install <local-path>`；`--local` 寫入 project settings（`.pi/settings.json`），預設寫入 global（`~/.pi/agent/settings.json`）。
- **依賴自動安裝（關鍵證據，原始碼 `core/package-manager.js`）**：
  - npm 來源：以 `npm install <spec> --prefix <install-root>` 裝入，**包含 dependencies**。
  - git 來源：`git clone` 到 `~/.pi/agent/git/<host>/<org>/<repo>`（或 project 對應目錄），**若倉根有 package.json 則在其內執行 `npm install`**（`installGit()` 第 1678 行起）。→ PMMeeting 可以把 `@fission-ai/openspec` 宣告為 dependency，用戶 `pi install` 後即自帶 OpenSpec CLI，**無須預裝**。
  - 版本 pinning：git 來源可帶 ref；`pi update` 重新解析；unpinned 的 git「臨時來源」（`-e`）每次載入自動 refresh。
- settings 支援 `+/-/!` 模式精細啟用/停用個別 extension/skill（可用来解衝突）。

### 1.2 Skill 發現與衝突（原始碼 `core/skills.js` + `core/package-manager.js` 查核）

**優先序（先找到者勝，collisions 產生 warning 級 diagnostic）**：

1. CLI `-e` 附帶的 skills（temporary）
2. **Packages**：project scope 套件 → user scope 套件（settings `packages` 陣列順序）
3. settings 中手動宣告的 local paths
4. Project `.pi/skills/`（需 project trusted）
5. Project `.agents/skills/`（含祖先目錄向上找，需 trusted）
6. User `~/.pi/agent/skills/`
7. User `~/.agents/skills/`

- **同 realpath（symlink 解開後同檔案）靜默去重** → 若兩處指向同一實體檔案不會碰撞。
- 名稱衝突：第一個載入者勝出，後續者記錄 `collision` diagnostic（`pi` 會顯示）。
- Skill 格式：目錄 + `SKILL.md`（frontmatter：`name`（小寫 a-z0-9-）、`description`）；模型依 description 自動觸發，`enableSkillCommands` 時可 `/skill:<name>` 顯式呼叫。
- **對 PMMeeting 的含義**：套件內 skill 優先於 project 端自動發現的 skill（如 OpenSpec init 寫入的 `.agents/skills/`）；vendored Superpowers 與用戶另裝的 superpowers 套件會撞名（`brainstorming` 等），需以「不暴露 vendored skills + 絕對路徑引用 + doctor 偵測」規避（見 04 文件 D2）。

### 1.3 Extension 機制（`docs/extensions.md` + 原始碼）

- TS/JS 模組，API：`pi.registerCommand(name, { description, getArgumentCompletions, handler })`、`pi.registerTool({...})`、事件掛載（`session_start`、`context`（每次 provider 請求前，可注入訊息）、`tool_call` 等）。
- 命令名衝突 → 自動加數字後綴（`/review:1`），**不**覆蓋。
- **Superpowers 的 bootstrap 模式（可直接參照的現成範例）**：116 行 extension，在 `context` 事件把 `using-superpowers/SKILL.md`（去 frontmatter）作為 user message 注入每個 provider 請求，強制「先檢查 skill 再行動」紀律。
- Extension 可取得自己所在套件根目錄 → 可以對模型公布「bundled skills 的絕對路徑清單」。

### 1.4 其它相關機制

- **Project trust**：project-local 的 extension/skill（`.pi/`、`.agents/`）需用戶 trust 該 project 才載入。
- `pi config` / settings 可逐資源啟用停用；`pi list` / `pi remove`。
- 本地開發：`pi install <dir>`（local source）或 `pi -e <ext> --skill <dir>`（臨時，免安裝）。

## 2. Superpowers（v7.0.2）

**分發**：git 只有（`github.com/obra/superpowers`；npm 上的 `superpowers@0.0.2` 是**佔位包**，非本尊）。git tags：v6.0.3…v7.0.2（本機副本位於 tag `v6.3.0` 後第 6 個 commit `22f0b46` = 「Release v7.0.2」）。
**本質**：它自己就是一個 Pi 套件（`pi-package` keyword；`pi.extensions: [./.pi/extensions/superpowers.ts]`、`pi.skills: [./skills]`），零 npm dependencies。

### 2.1 內容盤點

- **15 個 skills**（`skills/` 目錄）：`using-superpowers`（bootstrap 紀律）、`brainstorming`、`writing-plans`、`executing-plans`、`subagent-driven-development`、`dispatching-parallel-agents`、`test-driven-development`（含 `writing-good-tests.md` 附檔）、`systematic-debugging`、`verification-before-completion`、`requesting-code-review`、`receiving-code-review`、`using-git-worktrees`、`finishing-a-development-branch`、`writing-skills`、`diagnosing-superpowers`。
- **Extension**：如 1.3 所述，`context` 事件注入 using-superpowers bootstrap。
- **subagent 依賴**：`subagent-driven-development`、`dispatching-parallel-agents` 需要 subagent 工具（Pi 生態由 `pi-subagents` 套件提供 `subagent` 工具；無此工具時 fallback 到 `executing-plans` 本機執行）。

### 2.2 產出工件慣例（衝突點，整合必須處理）

| Skill | 預設產出位置 |
|---|---|
| `brainstorming` | `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`（committed） |
| `writing-plans` | `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`（開頭引用 spec 路徑） |
| `executing-plans` / `subagent-driven-development` | 消費 plan 檔、逐 task commit |

→ **與 OpenSpec 的 `design.md` / `tasks.md` 直接重疊**，是「單一真相來源」要求的核心矛盾，PMMeeting 必須在 workflow 層重導向（不改上游檔，見 02 文件對照表）。

### 2.3 版本化特徵

- `package.json` 有 `version` 欄位 + `RELEASE-NOTES.md` + git tag → pinning 可用 tag。
- 發布節奏快（數週內 v6.3→v7.0），skills 內容常調 → **必須 pin + lockfile**，且升級需回歸 workflow 冒煙測試。

## 3. OpenSpec（v2.0.0）

**分發**：npm `@fission-ai/openspec`（latest = 2.0.0；需 Node ≥ 22.12；unpacked ≈ 2.5MB）。另有 standalone binary（免 Node）與 Homebrew。
**本質**：兩層 — 終端 CLI + chat skills。

### 3.1 v2.0 破壞性變更（對整合設計極重要）

- **Skills-only 交付**：不再寫 `/opsx:*` 命令檔；每個命令等價於一個 skill（如 `/opsx:propose` → `openspec-propose` skill）。
- **單一共享副本**：skills 只寫一次到 **project 的 `.agents/skills/openspec-*`**，各工具目錄放 symlink（Pi 是官方支援工具，`skillsDir: '.pi'` → `.pi/skills/openspec-*` symlink）。被編輯過的舊副本會保留。
- `delivery` 設定退役（仍接受）、Amazon Q 退役、Windows 需 symlink 支援。
- 含義：**PMMeeting 不需自己實現 OpenSpec 的 skill 層**；`openspec init --tools pi` 會把官方 skills 正確裝進 project，Pi 自動發現（`.agents/skills` 在發現清單內）。

### 3.2 資料模型（project 內 `openspec/` 樹）

```
openspec/
├── config.yaml                 # profile、schema 選擇等
├── specs/<capability>/spec.md  # ★ 目前行為的 source of truth（長期資產）
├── changes/<change-id>/        # ★ 進行中的變更（workflow 單位）
│   ├── proposal.md             # 為什麼、改什麼
│   ├── specs/<capability>/spec.md  # delta specs（ADDED/MODIFIED/REMOVED Requirements）
│   ├── design.md               # 技術設計
│   └── tasks.md                # - [ ] checkbox 式任務清單（執行進度帳本）
└── changes/archive/YYYY-MM-DD-<id>/   # 完成後的變更
```

- **Schema 系統**：`schema.yaml` 定義 artifact 管線。解析優先序（原始碼 `src/core/artifact-graph/resolver.ts`）：project `openspec/schemas/<name>/` → user XDG → 套件內建（`spec-driven`）。→ PMMeeting 可放**自訂 schema** 而零改上游碼。
- **CLI 面**（查核 `src/commands/`）：`init`（含 `--tools` 工具偵測/選擇）、`list`、`show`、`validate [--json]`、`archive`、`update`、`instructions <artifact> [--json]`（**agent 契約：JSON 機器可讀指令**，含 `contextFiles`、task 的 `sourcePath`+`line` 等）、`status [--json]`、`workset`、`store`（beta）、`config`、`doctor`、`version`。
- **12 個官方 skills**：`openspec-explore`（探索/澄清需求）、`openspec-propose`（一步產出全套 artifacts）、`openspec-new-change`、`openspec-continue-change`、`openspec-update-change`、`openspec-ff-change`、`openspec-apply-change`（依 `instructions apply --json` 逐 task 實作、打勾 tasks.md）、`openspec-verify-change`（實作 vs artifacts 比對）、`openspec-sync-specs`、`openspec-archive-change`、`openspec-bulk-archive-change`、`openspec-onboard`。
- **Profile**：default（explore/propose/apply/archive 等）與 expanded（+new/continue/ff/bulk）。
- 版本狀態：2.0.0 為大改版（1.x 是 command-files 時代）→ pin 2.0.0 並以整合測試鎖住 CLI 行為。

## 4. 社群既有整合（prior art 與教訓）

### 4.1 opsx-superpowers（austinxyz，Claude Code plugin）＋兩篇部落格

- 形態：4 階段 `/opsx:explore → propose → apply → archive`，**硬邊界 gate**；`apply` 內建 TDD（red→green→commit）+ 每 task group 的 code review；plugin 內含 vendored Superpowers skills。
- 作者「五個摩擦點」與修法（對 PMMeeting 風險評估的直接輸入）：
  1. **brainstorm 的 UI 設計在 propose 時消失**（對話記憶是揮發的）→ 修法：mock 存成**檔案**（HTML），spec 以路徑引用。
  2. **brainstorm 不讀 codebase** → 修法：順序改為 **explore（讀碼）先於 brainstorm**。
  3. **skill 調度靠記憶而非機制**（最常咬人：忘了在 prompt 裡寫「用 TDD skill」，apply 就默默跳過）→ 修法：把 skill 序列**烤進命令/範本**，並用**檔案+路徑**取代自然語言作為工件間的連結媒介。
  4. **無 UI 驗證** → 修法：apply 階段 visual diff（soft gate）。
  5. **archive 沒有 retro**（教訓留在對話裡就蒸發）→ 修法：retro 寫入檔案、pitfalls 進 CLAUDE.md、spec 精粹遷入 README。
- 作者三級抽象演進：prompt+LLM 中介（會失真）→ **自訂 schema（可檢查的契約）** → plugin（可攜）。
- **與 PMMeeting 的差異**：Claude Code 專用；PMMeeting 要做 Pi 原生、自包含（含 CLI）、且上游雙 pinning。

### 4.2 superspec（danielhanold）

- 形態：**OpenSpec 當 orchestrator**（custom schema `openspec/schemas/superspec/` v4），6 階段管線，每階段在正確時機調用 Superpowers skill（brainstorm→artifact→TDD→review→branch 收尾）。「OpenSpec 管 WHAT（artifact 治理/驗證/歸檔），Superpowers 管執行紀律」。
- 教訓：custom schema 是讓 workflow 成為「工具可檢查契約」的關鍵機制；schema 本身是**資料**（YAML+templates），不動上游碼。

### 4.3 spec-driven-tdd（strelov1）

- 形態：多 harness skill-pack，以 `scripts/vendor-superpowers.mjs` **vendor Superpowers**（先例：vendoring 腳本 + 固定版本是社群已驗證做法）。

### 4.4 空白地帶（PMMeeting 的定位）

三者皆非 **Pi 原生自包含 package**：opsx-superpowers 綁 Claude Code 且要另裝 Superpowers；superspec 是 project 端 schema 不是套件；spec-driven-tdd 是 skill-pack 不管 CLI 與版本。→ **「一個 `pi install` 搞定 OpenSpec+Superpowers 的 Pi package」目前不存在**，PMMeeting 補的就是這個缺口。

## 5. 對 PMMeeting 的關鍵含義（研究結論摘要）

1. **自包含可行**：Pi 對 git/npm 套件會自動跑 `npm install` → `dependencies: { "@fission-ai/openspec": "2.0.0" }` 即達成「免預裝 OpenSpec」。
2. **Superpowers 只能 git vendor**（無真 npm 包）→ vendored copy + lockfile + sync 腳本（有社群先例）。
3. **重疊工件是已知矛盾**：design doc ↔ design.md、plan ↔ tasks.md；解法在 workflow 層重導向（orchestrator 契約），不動上游檔。
4. **skill 調度必須機制化**（Austin 摩擦點 3）：不能只靠 orchestrator prompt 提醒「記得用 TDD skill」→ PMMeeting extension 提供**狀態機 + gate 工具**，phase 推進與 skill 觸發由機制保證。
5. **OpenSpec 2.0 的 skills-only + `.agents/skills` 共享**與 Pi 的 skill 發現機制天然相容 → PMMeeting 的 init 階段直接跑官方 `openspec init`，零重寫。
6. **衝突面**：vendored Superpowers 與用戶另裝 superpowers 套件撞名 → 設計上「vendored skills 不進 pi.skills、以絕對路徑引用」+ doctor 偵測（04 文件 D2）。
7. **Pi 的 bootstrap 注入模式**（Superpowers extension 的 `context` 事件手法）是 PMMeeting orchestrator 紀律注入的現成範本。
